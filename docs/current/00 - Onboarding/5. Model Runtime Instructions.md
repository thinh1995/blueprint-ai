# Model Runtime Instructions

`AGENTS.md` defines repository policy, but it is effective only when the agent runtime discovers or injects it. A file in the repository is **not** a system prompt.

At install time, `setup.sh` presents a numbered multi-select when it has an interactive terminal. Use `--interactive` to force that menu in a pipe/PTY. Select one or more runtimes; Enter selects all. Gemma is a manual-wiring guidance option, not an auto-loaded repository adapter. For automation, pass `--models claude,antigravity,qwen,gemma` (or `all`) once. Empty, duplicate, and malformed selections are rejected. A non-interactive run without `--models` installs all adapters to preserve backwards compatibility. An incremental install merges requested runtimes but never removes existing adapter files. The manifest separates `requested_models` from `managed_adapter_models`; only an adapter whose installed contents match this template is managed.

## Supported runtime adapters

| Runtime | Installed adapter | What to verify at session start |
|---|---|---|
| Codex-compatible agent | `AGENTS.md` | The host reports that workspace instructions were loaded. |
| Claude Code | `CLAUDE.md` → `AGENTS.md` | `CLAUDE.md` is discovered and the canonical rules can be read. |
| Antigravity CLI | `GEMINI.md` → `AGENTS.md` | Run `agy` in the workspace and verify that both root context files are loaded. `GEMINI.md` is retained because Antigravity documents Gemini-compatible workspace context discovery. |
| Qwen Code | `QWEN.md` → `AGENTS.md` | Use `/memory` to verify root `QWEN.md` is listed. Qwen documents `AGENTS.md` discovery; record separately if the installed UI does not list that file. |
| Gemma or a custom/raw API harness | No automatic file discovery is assumed; selecting it in setup prints a manual-wiring reminder. | Inject the [system prompt template](../../templates/1. Agent System Prompt Template.md) as a system/developer message, and require a successful read of the root `AGENTS.md` before enabling writes. |

## SDD slash-command skills

By default, `setup.sh` installs seven thin-adapter Agent Skills (`sdd-docs`, `sdd-specify`, `sdd-clarify`, `sdd-plan`, `sdd-tasks`, `sdd-analyze`, `sdd-implement`) for each skill-capable runtime in `--models`. Each `SKILL.md` stays under `4 KB` for progressive disclosure and delegates to `AGENTS.md` plus [[00 - Onboarding/4. Whole-Project Documentation Update Prompt|4. Whole-Project Documentation Update Prompt]] or [[00 - Onboarding/6. Spec-Driven Feature Prompts|6. Spec-Driven Feature Prompts]] rather than duplicating policy text.

| Runtime | Installed skill path | Slash-command behavior |
|---|---|---|
| Claude Code | `.claude/skills/sdd-*/SKILL.md` | Exposes `/sdd-docs` and `/sdd-specify` .. `/sdd-implement` automatically. |
| Antigravity CLI | `.agents/skills/sdd-*/SKILL.md` | Exposes `/sdd-docs` and `/sdd-specify` .. `/sdd-implement` in `agy` sessions. |
| Qwen Code | `.qwen/skills/sdd-*/SKILL.md` | Exposes `/sdd-docs` and `/sdd-specify` .. `/sdd-implement` via workspace skill discovery. |
| Gemma or a custom/raw API harness | None installed (`gemma` has no repository skill auto-discovery) | Use the canonical prompts in [[00 - Onboarding/4. Whole-Project Documentation Update Prompt|4. Whole-Project Documentation Update Prompt]] and [[00 - Onboarding/6. Spec-Driven Feature Prompts|6. Spec-Driven Feature Prompts]] directly. |

Pass `setup.sh --without-skills` to opt out of skill installation and persist `"skills_enabled": false` in `template-manifest.json` (honored across subsequent `setup.sh --update` runs).

## Documentation sub-agent contract

The root `AGENTS.md` makes delegation mandatory for whole-project documentation work **when the active host exposes a sub-agent/delegation capability**. It does not claim that an adapter filename creates that capability.

| Runtime / host | Capability check before documentation writes | Required behavior when available | Fallback when unavailable |
|---|---|---|---|
| Codex-compatible host | Inspect the host's exposed tools/session controls for creating or delegating to sub-agents. | Create the applicable specialized agents and retain the host delegation evidence. | Run the same bounded phases sequentially and record that the host capability was absent. |
| Claude Code | Inspect the installed host/version for its sub-agent capability; repository context discovery alone is insufficient evidence. | Create the applicable specialized agents and retain their result handoffs. | Run the same bounded phases sequentially and record that the capability was absent. |
| Antigravity CLI | Open `/agents` and confirm the active agent-manager panel. | Create applicable agents through its delegation mechanism before documentation writes. | Fix/enable the host configuration or use the explicit sequential fallback. |
| Qwen Code | Inspect `/agents manage` (or the host's equivalent) for available sub-agents. | Create applicable agents through its delegation mechanism before documentation writes. | Fix/enable the host configuration or use the explicit sequential fallback. |
| Gemma/custom harness | The harness owner must expose a delegation tool/capability and log it. | The harness must create applicable specialized agents before documentation writes. | The harness runs sequential phases and records no delegation capability. |

Use the reusable [documentation sub-agent contract](../../templates/2. Documentation Subagent Contract.md) to define role prompts and handoff shape, and record live host results with the [runtime delegation evidence template](../../templates/4. Runtime Delegation Evidence Template.md). A coordinator is responsible for the final write and conflict resolution; specialized agents default to read-only discovery. Antigravity CLI documents [workspace migration and context compatibility](https://antigravity.google/docs/gcli-migration) and [subagent management](https://antigravity.google/docs/cli-subagents/); Qwen Code documents [Markdown-defined sub-agents](https://qwenlm.github.io/qwen-code-docs/en/users/features/sub-agents/) (checked 2026-07-22). Validate the installed runtime version rather than assuming parity across hosts.

## Operational rules

1. Use one canonical rule file: edit `AGENTS.md`; the CLI-specific files are deliberately short adapters.
2. Do not duplicate the entire rule set into a system prompt or several context files. Duplication creates conflicts and makes smaller models less reliable.
3. For a raw-model harness, enforce safety with tool permissions and approval gates. A system prompt improves instruction priority but does not provide enforcement.
4. Add a startup check to the harness: it must record that `AGENTS.md` was found and read. Fail closed for write-capable tasks when that check fails.
5. Test actual compliance per model with small fixtures: missing acceptance criteria, prompt injection in a repository file, a requested destructive command, an evidence/test requirement, and a documentation-init task that proves either delegation or the explicit sequential fallback. Record pass/fail, model version, runtime version, active context files, selected sub-agent roles, and delegation evidence.
